# Simple Docs

Help a reader do or understand something specific. Treat clarity, factual accuracy, and the reader's ability to find the next step as more important than sounding polished.

## Establish the job of the page

- Identify the intended reader, their goal, and what they can reasonably know already. Infer these from the request and nearby docs when possible; ask only if a missing answer would materially change the page.
- Follow the project's existing style, terminology, and format when they exist. For a new page, choose a tutorial, how-to, reference, or explanation shape according to the reader's need; do not mix them merely to fill a template.
- Gather facts from the supplied product behavior, code, configuration, examples, and existing docs. For a page from scratch, establish the supported steps, conditions, defaults, and expected results before drafting. Check consequential claims and examples against their sources. If essential behavior cannot be verified, ask for it or produce a clearly marked draft with specific open questions; do not invent the missing steps.

## Write from scratch or revise

- For a new page, write a complete path from the reader's starting point to the stated outcome. Put the task and outcome near the start, include only necessary prerequisites, and show how the reader can tell the task worked. Add troubleshooting only for likely blockers supported by evidence.
- For an existing page, make the smallest useful edit. Preserve valid facts, code fences, links, frontmatter, and intentional formatting unless the task calls for changing them.
- Use direct verbs, concrete nouns, and short paragraphs. Define unfamiliar terms when first needed. Prefer a small working example and a visible expected result when they help the reader act or check progress.
- State who or what performs each action, which version or condition a claim applies to, and what an instruction changes. Use exact names for commands, settings, and UI controls. Replace vague references such as "it," "this," or "as needed" when a reader could interpret them in more than one way. Do not shorten a sentence at the cost of changing its meaning.
- Remove repetition, generic praise, empty transitions, vague assurances, and claims that a step is "simple" or "seamless." Keep necessary nuance, warnings, and conditions even when they add length.
- Preserve useful author voice. Natural writing is specific and considerate; it does not need forced humor, chatty filler, or an artificial personality.

## Check from the reader's position

Review the result against the stated goal: Can the reader tell whether the page applies to them, begin with the stated prerequisites, follow the steps, recognize success, and recover from a likely failure? Point to the exact passage where any answer is missing. Treat this as an editorial check, not evidence that a real reader succeeded.

When usability matters, provide a brief reader test: give a new reader the page and one concrete task; ask them to work without coaching, note where they pause or seek outside help, and record whether they finish. Use actual feedback if supplied. Never report a simulated or self-reviewed pass as human test results.

## Deliver

Return the complete new page, the revised page, or edit the requested files. Summarize consequential choices and any factual questions that still need an owner. If a real reader test has not happened, say so only when the user asked about usability or validation.
